RestoreCheck

Automated backup recoverability verification on AWS

Cloud storage keeps backups durable: the bytes are not lost. It does not prove they are recoverable. A backup can be complete on disk yet missing a table, silently corrupted, or encrypted with a key that no longer works. RestoreCheck proves recoverability the only way that counts: it regularly restores the newest database backup into a temporary copy, checks the data inside it, records the result, alerts on failure, and always deletes the copy.

How a run works

  1. 1
    Schedule

    EventBridge starts a run (nightly, or on demand)

  2. 2
    Restore

    The newest RDS snapshot is restored into a temporary instance

  3. 3
    Wait

    Step Functions polls until the copy is available, with no Lambda time limit

  4. 4
    Verify

    A Lambda inside the VPC logs in with an IAM token and runs the checks

  5. 5
    Tear down

    The temporary instance is deleted on every path, including failures

  6. 6
    Record and alert

    Report to S3, history to DynamoDB, metrics to CloudWatch, email via SNS

Results: every kind of damage is caught

For each scenario the demo database was reset, damaged in one specific way, and backed up, then RestoreCheck verified that backup. A trustworthy verifier must pass the healthy backup and catch every broken one.

The integrity checks

CheckWhat it proves
instance_availableThe restore produced a usable instance of the right engine
connectThe restored database is reachable and login works (IAM token over TLS)
tables_presentEvery expected table exists
row_countsEach table has at least its expected number of rows
canary_checksumA known table's content matches byte-for-byte
test_queriesApplication-level queries hold, e.g. no orphaned rows

Built with

Amazon EventBridge, AWS Step Functions, AWS Lambda (Python 3.12), Amazon RDS for PostgreSQL, Amazon VPC, Amazon DynamoDB, Amazon S3, Amazon SNS, Amazon CloudWatch and AWS IAM, deployed as code with AWS SAM / CloudFormation. Each Lambda has its own least-privilege custom IAM policy, and the checker logs in with IAM database authentication, so no database password is stored anywhere.
